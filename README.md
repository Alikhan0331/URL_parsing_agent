# URL Parsing Agent

Автономный агент на LangGraph, который обходит сайты со списком новостей (пагинация вида
`?page=N`), находит карточки-статьи и сохраняет только те из них, которые ДЕЙСТВИТЕЛЬНО
релевантны Президентскому центру Республики Казахстан (ПЦ) - будь то главная тема статьи,
место проведения мероприятия или упоминание его руководства/сотрудников. Работает автономно
по расписанию (Docker + APScheduler) и инкрементально - каждый день дозаписывает только новые
статьи, не трогая уже проверенные.

## Как это работает

Вся логика обхода одного сайта реализована ОДИН раз - в виде LangGraph-графа
(`src/event_agent/graph/` + `src/event_agent/nodes/`). Его использует и продакшен-планировщик,
и ручной разовый прогон - разница только в том, передаётся ли графу sqlite-соединение.

```
list_page --(fan-out по карточкам)--> extract_event --> classify_topic --(edge)--> keep_record   --\
    ^                                                                   \-> discard_record --/      |
    |                                                                                                v
    \------------------------------------- next_page <----------------------------------------------/
```

1. **`list_page`** скачивает страницу списка (с fallback на headless-браузер, если сайт рендерит
   контент через JS) и находит ссылки на карточки по структуре разметки
   (изображение + заголовок), без хардкода под конкретный сайт.
   - Каждый структурно найденный кандидат **обязательно перепроверяется LLM**
     (`verify_candidates_with_llm`) - блок с такой же вёрсткой, но другим смыслом
     (карточка партнёра, вакансия и т.п.), должен быть отклонён.
   - Если структурная эвристика не нашла вообще ничего, в дело вступает LLM-фолбэк
     (`classify_links_with_llm`) - модель сама смотрит на все ссылки страницы.
   - В инкрементальном режиме (когда графу передано sqlite-соединение) ссылки, уже
     доведённые до финального решения ранее (`processed_urls`), отбрасываются, а если
     весь остаток страницы уже виден - обход останавливается.
2. **`extract_event`** скачивает самую статью и вытаскивает title / og:image / основной
   текст (через `trafilatura`).
3. **`classify_topic`** решает, релевантна ли статья Президентскому центру. Сначала ищет
   ДОСЛОВНОЕ упоминание фразы «Президентский центр» в тексте (регэксп, без LLM) - если
   упоминания нет вообще, статья отклоняется мгновенно и без обращения к модели. Если
   упоминание есть, LLM получает точные цитаты и текст статьи и решает, содержательная
   это связь (главная тема, место проведения мероприятия, работа сотрудников ПЦ) или
   случайная (ПЦ просто в общем списке учреждений УДП). Модель отдельно предупреждена
   не путать ПЦ с похожими по названию учреждениями УДП (Дворец Независимости, ТРК
   Президента, Медицинский центр, Инженерно-технический центр).
4. **`keep_record` / `discard_record`** - условный edge по результату шага 3. В инкрементальном
   режиме оба узла также пишут решение в `processed_urls`, а `keep_record` дополнительно
   сохраняет статью в таблицу `articles`.
5. **`next_page`** переходит на следующую страницу, если не достигнут лимит страниц и не
   вся страница состояла из уже обработанных ссылок.

## Структура проекта

```
src/event_agent/
├── config.py                 # env-переменные и константы (Ollama, троттлинг, таймауты)
├── config_sites.py           # Pydantic-модель конфигурации сайтов, грузится из config/sites.json
├── graph/
│   ├── state.py               # CrawlState, EventRecord
│   ├── builder.py              # сборка графа: узлы + условные edges
│   └── router.py               # функции-роутеры для условных edges
├── nodes/
│   ├── list_page.py             # скачивание страницы списка + структурный/LLM фильтр карточек
│   ├── extract_event.py          # извлечение title/текста/картинок конкретной статьи
│   ├── classify_topic.py          # проверка релевантности статьи Президентскому центру
│   ├── topic_gate.py               # keep_record / discard_record + запись в БД
│   └── pagination.py                # инкремент номера страницы
├── tools/
│   ├── fetcher.py              # HTTP (httpx) + headless-браузер (Playwright) fallback, троттлинг
│   ├── parser.py                # структурная эвристика карточек + извлечение статьи
│   ├── dom_utils.py              # общие хелперы для анализа DOM (фильтр навигации/меню)
│   ├── llm_classifier.py          # весь LLM-слой: верификация карточек, фолбэк-классификация
│   │                                 ссылок, проверка релевантности ПЦ (Ollama)
│   └── odoo_client.py             # ЗАГОТОВКА на будущее, пока НЕ подключена ни к одному пайплайну
├── storage/
│   └── db.py                    # SQLite: таблицы articles (сохранённые статьи) и
│                                  processed_urls (все проверенные URL, для инкрементальности)
├── pipeline/
│   ├── daily_scan.py             # тонкая обёртка над графом для продакшен-обхода одного сайта
│   └── runner.py                  # оркестрация полного суточного прогона по всем сайтам
└── utils/
    ├── logging.py                 # настройка логирования
    └── retry.py                    # общий tenacity-ретрай

scripts/
├── run_crawl.py               # ручной разовый прогон ОДНОГО сайта по URL, пишет output/events.json
├── run_daily.py               # ручной триггер полного суточного прогона (без ожидания расписания)
├── scheduler.py                 # долгоживущий процесс планировщика (точка входа Docker-контейнера)
└── inspect_db.py                 # просмотр сохранённых статей в output/articles.db

config/sites.json              # список сайтов + расписание (schedule_time, timezone)
docker/                         # Dockerfile + docker-compose.yml
output/                         # articles.db, events.json, debug/ - создаётся автоматически, в git не попадает
```

## Быстрый старт (без Docker)

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -e .
playwright install chromium
cp .env.example .env
```

Откройте `.env` и при необходимости поправьте `OLLAMA_BASE_URL`/`OLLAMA_MODEL` (нужен
запущенный локально Ollama с загруженной моделью, например `ollama pull llama3.1:8b`).

**Разовый обход одного сайта** (без сохранения в БД, результат - JSON):

```bash
python scripts/run_crawl.py --base-url "https://qr-pib.kz/ru/post/?page={n}" --max-pages 3
```

Результат появится в `output/events.json`.

**Полный суточный прогон по всем сайтам из `config/sites.json`** (с сохранением в SQLite):

```bash
python scripts/run_daily.py
```

## Запуск в Docker (продакшен-режим)

Это то, как агент реально работает автономно - планировщик поднимается в контейнере и сам
запускает обход по расписанию из `config/sites.json` (поле `schedule_time`, `timezone`).

```bash
cp .env.example .env        # если ещё не создан
docker compose -f docker/docker-compose.yml up --build -d
```

При старте контейнер сразу выполняет один прогон (не дожидаясь расписания), затем
встаёт в режим ожидания следующего запуска по cron.

Полезные команды:

```bash
# логи в реальном времени
docker compose -f docker/docker-compose.yml logs -f event-agent-scheduler

# ручной запуск прогона без пересборки и без ожидания расписания
docker compose -f docker/docker-compose.yml exec event-agent-scheduler python scripts/run_daily.py

# посмотреть сохранённые статьи
docker compose -f docker/docker-compose.yml exec event-agent-scheduler python scripts/inspect_db.py

# остановить
docker compose -f docker/docker-compose.yml down
```

`config/sites.json` смонтирован как volume - чтобы изменить список сайтов или расписание,
достаточно отредактировать файл на хосте и перезапустить контейнер (пересборка образа не
нужна):

```bash
docker compose -f docker/docker-compose.yml restart
```

## Как добавить новый сайт

Отредактируйте `config/sites.json`, добавив объект в массив `"sites"`:

```json
{
  "name": "my-site",
  "base_list_url": "https://example.kz/news/?page={n}",
  "list_root_path": null,
  "max_pages_per_run": 2
}
```

- `name` - идентификатор для логов и колонки `site` в БД.
- `base_list_url` - шаблон URL страницы списка, `{n}` - номер страницы.
- `list_root_path` - опциональный доп. фильтр по разделу сайта (обычно не нужен -
  структурная эвристика и так отличает карточки от навигации).
- `max_pages_per_run` - сколько страниц пагинации проверять за один прогон (инкрементальный
  обход сам остановится раньше, если упрётся в уже виденный контент).

Никакого поля для ключевых слов нет - релевантность Президентскому центру проверяется LLM
для каждой статьи автоматически (см. раздел «Как это работает»).

## Переменные окружения (`.env`)

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `OLLAMA_BASE_URL` | `http://localhost:11434` | адрес Ollama |
| `OLLAMA_MODEL` | `llama3.1:8b` | модель для верификации карточек и проверки релевантности ПЦ |
| `USE_LLM_FALLBACK` | `true` | включает LLM-классификацию ссылок, если структурная эвристика ничего не нашла |
| `LLM_VERIFY_STRUCTURAL` | `true` | включает обязательную LLM-верификацию структурно найденных карточек |
| `MAX_PAGES` | `5` | лимит страниц по умолчанию для `scripts/run_crawl.py` |
| `REQUEST_TIMEOUT` | `15` | таймаут HTTP-запросов, сек |
| `REQUEST_DELAY_SECONDS` | `1.5` | пауза перед каждым запросом (защита от бана по IP) |
| `USER_AGENT` | `Mozilla/5.0 (compatible; URLParsingAgent/1.0)` | User-Agent для запросов |
| `ODOO_URL`, `ODOO_DB`, `ODOO_USERNAME`, `ODOO_PASSWORD` | пусто | заготовка на будущее, `tools/odoo_client.py` пока НЕ подключён ни к одному пайплайну |

## Хранилище

`output/articles.db` (SQLite) создаётся автоматически при первом запуске. Две таблицы:

- **`articles`** - только статьи, признанные релевантными ПЦ (`url`, `site`, `title`,
  `body_text`, `images`, `matched_keywords` - на самом деле хранит обоснование LLM, не
  ключевые слова, `discovered_at`).
- **`processed_urls`** - ВСЕ URL, когда-либо доведённые до финального решения (и
  сохранённые, и отклонённые), с полями `is_relevant` и `reason`. Используется, чтобы
  инкрементальный обход не перепроверял одни и те же отклонённые статьи повторно каждый
  день.

Посмотреть содержимое:

```bash
python scripts/inspect_db.py                  # все сохранённые статьи
python scripts/inspect_db.py --site qr-pib     # только по одному сайту
python scripts/inspect_db.py --full            # с полным текстом статьи
```

## Отладка

При каждом обходе страницы списка и каждом LLM-решении в `output/debug/` сохраняются
подробности:

- `list_page_<N>.html` - сырой HTML страницы списка (если структурная эвристика ничего не нашла)
- `llm_decisions_<url>.json` - обоснование каждого решения LLM по каждой ссылке/статье

## Известные ограничения

- LLM-верификация карточек и проверка релевантности ПЦ выполняются последовательно по одной
  статье за раз - на страницах с 10+ кандидатами это может занимать 1-2 минуты на
  сайт при использовании небольшой локальной модели.
- `tools/odoo_client.py` - нерабочая заготовка, интеграция с Odoo не реализована.
- Автотестов в проекте нет - основной способ проверки корректности фильтрации сейчас это
  просмотр `output/debug/llm_decisions_*.json` и ручная сверка с реальным содержимым сайта.
